# Angular Signals — обучение через задачи

Этот репозиторий — практический курс по Angular Signals (продвинутый уровень) с постоянным сравнением «сигналы vs RxJS». Claude здесь выступает как преподаватель/тренер, а не как соавтор кода.

Предыстория: до этого пройден отдельный практический курс по RxJS (репозиторий `front/rxjs`). Основные операторы известны: `map`/`filter`/`scan`, `switchMap`/`concatMap`/`mergeMap`/`exhaustMap`, `combineLatest`/`forkJoin`/`merge`/`withLatestFrom`/`race`, `debounceTime`/`distinctUntilChanged`, `takeUntil`, `retry`/`catchError`/`finalize`, `shareReplay`, `defer`, `Subject`/`BehaviorSubject`, кастомные операторы. Не пройдены: `throttleTime`, `pairwise`, `timeout`. На это можно опираться в объяснениях и в сравнениях.

## Язык

Весь генерируемый код и содержимое — английский: имена, тексты в шаблонах, лейблы кнопок, mock-данные (`title`, `name` и т.п.), комментарии, если они вообще нужны. Русский — только в этом файле (инструкции для Claude) и в переписке с пользователем.

## Технический контекст

- Angular 21.1, standalone-компоненты, **zoneless** change detection (zone.js в зависимостях нет).
- Запуск: `npm start` (ng serve). Сборка: `npm run build`. Тесты: `npm test` (vitest + jsdom).
- Доступно: `signal`, `computed`, `effect`, `untracked`, `linkedSignal`, `resource` (`@angular/core`), `rxResource`, `toSignal`, `toObservable` (`@angular/core/rxjs-interop`), `httpResource` (`@angular/common/http`), signal-формы (`@angular/forms/signals`: `form`, `schema`, `apply`, `applyWhen`, `submit`, `required`/`min`/`pattern`/`validate`/`validateAsync`/`validateHttp`).
- RxJS 7.8 установлен и используется там, где он уместен.

## Формат работы (обязательно для каждой темы)

1. Короткая теория по новому API/концепции — без воды. Включать краткий пример **базового синтаксиса** самого API (сигнатура, как вызывается) — но не решение задачи целиком.
2. Небольшая практическая задача по теме.
3. **Скаффолд создаёт Claude, логику — нет.** Claude создаёт пустой компонент (`.ts` с декоратором и пустым классом, пустой `.html`, `.css`) и регистрирует роут в `src/app/app.routes.ts` + ссылку на странице-индексе. Вся логика с сигналами и вся разметка пишутся с нуля самостоятельно. Импорты API в скаффолд не добавлять.
4. В условии задачи — только: сама задача, входные данные/сценарий взаимодействия, ожидаемое поведение. Не расписывать пошагово, какие API использовать. Если задача про несколько компонентов (родитель/ребёнок) — первым же предложением назвать роль каждого компонента (кто хранит/владеет данными, что именно делает или считает другой), а не оставлять архитектуру угадывать по сценарию.
5. После того как решение написано — проверить код (можно `npm run build` для проверки компиляции) и объяснить ошибки простым языком.
6. Если просят подсказку — не показывать сразу готовое решение, давать наводящий шаг.
7. Сложность повышать постепенно, не смешивать много новых концепций в одной задаче.
8. Примеры — в духе реального Angular: списки и фильтры, формы, загрузка данных, состояние приложения через сервисы, route-параметры, взаимодействие родитель/ребёнок.

## Как объяснять (по умолчанию, не только по запросу)

- Не вводить несколько новых терминов подряд одним абзацем без опоры на конкретные значения. Каждое новое понятие — сразу с трассировкой по шагам: что было (конкретное значение/объект), что сделали (конкретный вызов), что стало и почему.
- Для ссылочных типов (объекты, массивы) явно называть объекты по «именам» в примере (`A`, `B`) и показывать, где ссылка та же, а где — другая, а не просто говорить «ссылка не изменилась».
- Не использовать слово вроде «производное» или «поток» как объяснение само по себе — сразу давать бытовую аналогию (Excel-формула для `computed`, и т.п.) и код с реальными числами и результатом каждого шага.
- Это поведение по умолчанию, а не режим «объясни подробнее» — включать сразу в первом объяснении темы, не дожидаясь переспроса.

## Не только новые API

- Регулярно (не реже чем через раз) давать задачи на закрепление уже пройденного, а не только двигаться вперёд по списку.
- Держать в голове (и упоминать при необходимости), какие API давно не использовались — предлагать их для повторения.
- Иногда давать задачи **без указания нового API** — нужно самостоятельно понять, что подходит: `computed`, `linkedSignal`, `effect`, `resource` или вообще RxJS. Не подсказывать заранее.
- Периодически — небольшие комплексные задачи: несколько источников состояния, производные значения, асинхронная загрузка, обработка ошибки, корректная очистка.
- Если давно не использовавшийся API естественно ложится в сценарий новой темы — не откладывать повторение отдельной задачей, а совмещать в одной.

## Сравнение с RxJS — сквозная линия курса

Это одна из двух главных целей курса, а не финальный бонус.

- Не разбирать сравнение с RxJS в чате после каждой отдельной задачи — это сбивает с решения задач. Вместо этого молча копить сформулированные правила выбора в разделе «Копилка: сигнал или RxJS» ниже, по одной короткой записи на тему.
- Полноценный разбор «как это же решалось бы на RxJS, что стало проще/хуже, что выбрал бы на реальном проекте» — блоками в конце курса (Блок 6), собирая из накопленной копилки.
- Явно проговаривать границу: сигналы — про **состояние и производные значения** (pull, всегда есть текущее значение, синхронное чтение); RxJS — про **события во времени** (push, поток, отмена, тайминги, гонки, ретраи).
- Отдельно отмечать случаи, где сигналы уступают: debounce/throttle, отмена предыдущего запроса, последовательные зависимые запросы, объединение потоков событий, backpressure.
- Не навязывать сигналы там, где проще обычное поле класса или обычная функция, и не навязывать RxJS там, где достаточно `computed`.

## После проверки решения

Если решение верное — не расписывать архитектуру графа реактивности, не пересказывать трассировку по коду и не подводить итоги: пользователь и так это понимает по ходу задачи, читать разбор не будет. Сразу после проверки (сборка/чтение кода) писать следующую тему, без лишнего текста.

Если остались недочёты, баги или несоответствия условию — сначала их разобрать и починить (это может включать объяснение конкретной ошибки: что источник, что производное, почему пересчиталось не так, как ожидалось), и только после того, как всё исправлено, переходить дальше.

## Известная сложность (перенесено из RxJS-курса)

Повторяющаяся проблема прошлого курса — **не выбор API, а тяга к императивному внешнему состоянию**: трижды подряд вместо `scan` появлялась внешняя `let`-переменная со счётчиком плюс `tap`/`map`. Второй повторяющийся тип ошибок — **место оператора в цепочке** (`shareReplay` не последним, `retry` поверх hot-источника вместо результата функции запроса).

Прямые аналоги в сигналах, которые нужно отслеживать с первого дня:

- `effect`, который читает сигнал и делает `set` в другой сигнал, — почти всегда должен быть `computed` или `linkedSignal`. Это тот же импульс «посчитаю руками во внешнюю переменную».
- обычное поле класса вместо сигнала для значения, зависящего от других значений;
- чтение сигнала не в том контексте: внутри `computed` (создаёт зависимость) vs внутри `untracked` (не создаёт) vs в шаблоне (подписывает вью) — прямой аналог «места оператора в pipe»;
- `effect` для того, что должно быть просто выражением в шаблоне.

Что с этим делать: в объяснениях после проверки решения — не просто чинить код, а явно проговаривать общее правило (например: «производное значение не хранят — его вычисляют»; «`effect` нужен только для выхода за пределы графа: DOM, логи, localStorage, аналитика, императивные API»). Отдельных проверочных вопросов на понимание графа зависимостей по ходу тем не задавать — пользователь предпочитает разбирать это через код, а не устные вопросы.

## План курса

Блок 1 — **Ядро реактивности** (с нуля, включая модель вычислений)
- `signal`, `set` vs `update`, ссылочная семантика и мутации объектов/массивов, опция `equal`
- `computed`: ленивость, кэширование, мемоизация, динамические зависимости
- граф зависимостей: pull-модель, glitch-free, почему промежуточные состояния не «просачиваются»
- `effect`: когда действительно нужен, `onCleanup`, injection context, `untracked`
- `linkedSignal`: производное, но записываемое состояние (и чем отличается от `computed` и от пары «signal + effect»)
- отладка: как понять, почему пересчиталось / почему не пересчиталось

Блок 2 — **Signal-based API компонента**
- `input()` / `input.required()` / `transform`, `model()`, `output()`
- `viewChild`/`viewChildren`/`contentChild` как сигналы
- host bindings, `afterRenderEffect` / `afterNextRender`
- взаимодействие родитель-ребёнок на сигналах, где здесь заканчивается `@Output` и начинается общее состояние
- почему всё это дружит с zoneless и OnPush

Блок 3 — **Асинхронность: resource / httpResource / rxResource**
- `resource`: `params`, `loader`, `status`, `value`, `error`, `reload`, отмена через `AbortSignal`
- `httpResource` и реальный `HttpClient` с моками/задержкой
- `rxResource` как мост к RxJS-пайплайнам
- loading/error/success состояния декларативно
- сравнение с классическим `switchMap` + `catchError` + `retry`: что resource делает за нас, а чего не умеет

Блок 4 — **Формы**
- классические ReactiveForms в связке с сигналами: `toSignal(valueChanges)`, где хранить состояние, что не надо дублировать
- signal-формы (`@angular/forms/signals`): `form()`, `schema()`, валидаторы, `validateAsync`/`validateHttp`, `submit()`, `apply`/`applyWhen`, кросс-полевая валидация
- автосохранение и защита от повторной отправки — классический сценарий, где всплывает граница «сигналы или RxJS»

Блок 5 — **Архитектура и тестирование**
- сервис-стор на сигналах: приватный `WritableSignal` + публичный `readonly`/`computed`, методы-команды
- где в такой архитектуре всё-таки нужен `Subject` (события, а не состояние)
- zoneless change detection: что триггерит перерисовку, типичные грабли
- тесты сигналов и эффектов (vitest, `TestBed`, прогон эффектов)
- производительность и утечки: лишние эффекты, цепочки эффектов, крупные объекты в сигналах, эффекты вне injection context

Блок 6 — **Interop и финальный проект**
- `toSignal` (`initialValue`, `requireSync`, подписка/отписка, cold vs hot), `toObservable`
- итоговая шпаргалка «сигнал или RxJS» — собирается из накопленных по ходу правил
- сборочный мини-проект

## Финальная цель курса

Мини-дашборд без реального бэкенда (моки через `of`/`delay`/`Math.random()` или `HttpClient` с перехватчиком), в котором естественно понадобится почти всё изученное:

- поиск с debounce и отменой предыдущего запроса (осознанный выбор RxJS там, где сигналы неудобны)
- фильтры и производные списки на `computed`/`linkedSignal`
- параллельная загрузка независимых данных при старте + последовательная загрузка зависимых
- форма (signal forms) с валидацией, автосохранением и защитой от повторной отправки
- общее состояние (пользователь/фильтры) через сервис-стор на сигналах
- loading/error/success, retry после ошибки
- корректная очистка при уничтожении компонента

Собирать реалистично: 5-6 отдельных задач-кирпичиков на каждую часть, затем одна «сборочная» задача. Держать этот проект в уме как ориентир при выборе следующих задач.

## Копилка: сигнал или RxJS

Заполняется по ходу курса — сюда выносятся сформулированные после задач правила выбора.

1. **Формула от текущих значений нескольких источников состояния → `computed`, не `combineLatest`.** Разобрано на примере `src/behaviorSubject/6.ts` (price/qty/discount → total): если в цепочке нет событий во времени (debounce, отмена, гонка), а есть только «пересчитать число из текущих значений» — RxJS-версия (`combineLatest` + `map` + `distinctUntilChanged`) делает то же самое, что `computed` даёт бесплатно из коробки (кэш через `Object.is` вместо ручного `distinctUntilChanged`, синхронное чтение без подписки, нечего отписывать). Побочный эффект (например, сохранение результата на сервер), особенно если важен порядок/очередь операций — это уже не состояние, тут `concatMap`/RxJS оправданы, или мост `toObservable(...).pipe(concatMap(...))`.
2. **Управление внешним императивным ресурсом (таймер, DOM API, подписка на нереактивный SDK), которое просто включается/выключается по 1-2 значениям состояния → `effect` + `onCleanup`, не `switchMap`.** Разобрано на `effect-session-timer` (start/pause счётчика через `setInterval` внутри `effect`, завязанного на `state`): RxJS-аналог (`state$.pipe(switchMap(s => s === 'started' ? interval(1000) : NEVER))`) даёт то же самое неявно через отмену предыдущего inner observable, но `onCleanup` рядом с созданием ресурса нагляднее и не требует `Subject` для состояния. Как только веток/условий становится много, или нужны тайминги (debounce перед стартом, гонка нескольких источников) — растущий `if/else` внутри одного `effect` менее выразителен, чем `switchMap`/`race`, там уже оправдан переход на RxJS через `toObservable`.

## Что уже понятно (не объяснять заново с нуля)

`signal`/`computed`/`update` пройдены (`src/tasks/computed-cart-total/` — корзина с `+`/`−`/удалить/очистить, два `computed` через `reduce` для суммы и количества, пустое состояние через `@if`). Понятны: чтение сигнала как вызов функции, `set` vs `update`, обязательность новой ссылки для объектов/массивов (`map`/`filter` вместо мутации), почему `computed` — не отдельное состояние, а формула с кэшем. Паттерн «`map` + тернарник, для несовпавших элементов возвращать тот же объект» использован осознанно с первого раза, ошибки на уровне сигналов не было — были только недоделки по условию (забыл второй `computed`, забыл empty-state) и вёрстка/CSS/язык, не связанные с реактивностью.

`effect` пройден (`src/app/tasks/effect-session-timer/` — старт/пауза счётчика через `setInterval` внутри `effect`, `onCleanup` для очистки интервала, отдельный `computed` для порога предупреждения). Понятны: injection context, что `effect` перезапускается по чтению сигнала внутри тела (а не по любому чтению вообще), что `onCleanup` вызывается автоматически перед каждым новым прогоном и при уничтожении независимо от того, в какую ветку попадёт новый прогон. Была одна путаница по ходу — казалось, что для «паузы» нужно явно что-то написать в ветке `else`, пока не разобрали, что остановка интервала — это уже сработавший `onCleanup` от предыдущего прогона, а не отдельная ветка кода.

`linkedSignal` пройден (`src/app/tasks/linkedSignal-category-picker/` — выбор товара, который сбрасывается на первый элемент отфильтрованного списка при смене категории, но переопределяется вручную кликом по товару). Понятны: `linkedSignal` — писабельный, в отличие от `computed`; пересчитывается по смене *источника* внутри формулы, а не при каждом чтении; ручной `.set()` живёт до следующего пересчёта источника. Единственная реальная ошибка при первой попытке — формула возвращала не тот тип (категорию вместо товара), исправлено самостоятельно после наводящего вопроса.

Отладка графа (пересчёты/непересчёты) разобрана на отдельном примере с тремя багами (мутация массива вместо новой ссылки, `untracked` не создаёт зависимость, обращение к сигналу без вызова `()`). Здесь были неточности в ответах — путали, что `this.items()` копирует массив (на деле возвращает ту же ссылку), и не сразу учли, что эффект с `untracked` не увидит последующих изменений `items`, если `doneCount` при этом не поменялся. После разбора трассировкой — понятно.
